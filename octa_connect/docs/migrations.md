# Migrations — الحقول والحالات والقيود الجديدة

مطلوب صراحة في OC05-21. **لا قاعدة بيانات Odoo فعلية في أي جولة من هذا
المشروع** — لذلك لا migration واحدة هنا شُغِّلت فعليًا. هذا الملف يوثّق
بصدق ما يلزم تنفيذه، بصيغة Odoo القياسية (`pre_init_hook`/`post_init_hook`
أو ملفات `migrations/<version>/`)، **NOT RUN بالكامل**.

## مبدأ عام (كما ينص OC05-21 حرفيًا)
- لا إعادة بناء شاملة، ولا حذف بيانات لتسهيل الاختبارات.
- التوقيتات المفقودة تاريخيًا تظل مجهولة (`None`) — لا تُملأ بتاريخ الترحيل.
- لا تصنيف حالات `available` قديمة كـ`confirmed` بلا دليل فعلي.
- قبل فرض أي `unique constraint` جديد: افحص تعارضات البيانات القائمة أولًا
  وأصدر تقريرًا، لا تفرض القيد صامتًا فيفشل التثبيت لاحقًا بلا تفسير.

## الحقول الجديدة المطلوبة هذه الجولة (Gate E) وأثرها على بيانات قائمة

| الحقل/النموذج | التأثير على upgrade | ملاحظة الترحيل |
|---|---|---|
| `octa.hub.brand` (نموذج جديد كامل) | آمن — نموذج جديد، لا صفوف قديمة تتأثر | لا حاجة لـmigration خاصة، فقط تثبيت عادي |
| `octa.hub.branch.brand_id` (حقل جديد، اختياري) | آمن — nullable، الفروع القائمة تبقى بلا براند حتى تُصنَّف يدويًا | **لا تُخمِّن** براندًا افتراضيًا لفروع قائمة — يبقى `False` صراحة |
| `octa.hub.order` (لا حقل جديد هذه الجولة، لكن مخطط له لاحقًا: حقول توقيت صريحة لكل مرحلة من OC05-14) | — | مؤجَّل لجولة قادمة؛ عند إضافته: القيم التاريخية المفقودة = `None`، لا تُشتق من `create_date` |
| قيد فريد جديد محتمل مستقبلًا على `ExternalMapping` بحسب (`source_system`, `source_connection`, `entity_type`, `external_id`) | **يحتاج تقرير تعارضات أولًا** — لم يُبنَ هذا الموديل في Odoo بعد (لا يزال pure-Python فقط في `lib/external_mapping.py`) | عند بنائه في Odoo: شغّل استعلام تعارضات قبل `ALTER TABLE ... ADD CONSTRAINT`، ولا تفرضه على بيانات لم تُفحص |

## خطة عامة لأي migration مستقبلية (نمط قياسي لم يُشغَّل بعد)

```python
# addons/octa_hub_core/migrations/19.0.2.0.0/post-migrate.py  (NOT RUN — مثال فقط)
def migrate(cr, version):
    # 1. افحص التعارضات قبل أي قيد جديد
    cr.execute("""
        SELECT source_system, external_id, COUNT(*)
        FROM octa_hub_external_mapping
        GROUP BY source_system, external_id HAVING COUNT(*) > 1
    """)
    conflicts = cr.fetchall()
    if conflicts:
        # سجّل تقريرًا، لا تفرض القيد، أوقف وأبلغ المسؤول
        raise Exception(f"{len(conflicts)} تعارضًا يجب حله يدويًا قبل فرض القيد")
    # 2. فقط بعد صفر تعارض، أضف القيد
    cr.execute("ALTER TABLE octa_hub_external_mapping ADD CONSTRAINT ...")
```

## اختبار Upgrade (مطلوب صراحة، NOT RUN)
القبول المطلوب: "تثبيت نظيف وupgrade على نسخة بيانات اختبار ممثلة يحافظان
على المعرفات والطلبات والمبالغ والصور." خطوات إعادة الإنتاج (بعد توفر Odoo):

```bash
# 1. تثبيت نظيف + بيانات تجريبية (demo_data.xml)
odoo-bin -d octa_test -i octa_hub_core --stop-after-init
# 2. تسجيل معرفات/مبالغ عينة للمقارنة (يدويًا أو سكربت تحقق)
# 3. تحديث لنسخة تالية من الكود
odoo-bin -d octa_test -u octa_hub_core --stop-after-init
# 4. قارن نفس المعرفات/المبالغ — يجب أن تتطابق تمامًا
```
هذا **لم يُشغَّل ولا مرة واحدة** في أي جولة من هذا المشروع — لا Odoo/
PostgreSQL في بيئة التطوير. راجع `docs/RUNBOOK.md` القسم 2/6.

## Backup / Rollback (موثَّق، NOT RUN)
لا توجد بيانات إنتاج في هذا المشروع (بيانات اختبار `[TEST]` فقط)، فلا خطة
rollback فعلية مطلوبة الآن. عند وجود بيئة إنتاج فعلية مستقبلًا: نسخة
احتياطية لقاعدة البيانات قبل أي `-u` (upgrade)، واختبار استعادة تلك النسخة
فعليًا (لا افتراض نجاحها) قبل اعتماد الترقية — هذا نفسه بند مؤجَّل غير
مُختبَر (F-VERIFY سابقًا في audit-findings.md).
